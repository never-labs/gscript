MethodJIT 模块化优化器管线

这里的“模块化优化器管线”指：Tier2 编译不再只是一段固定的手写 pass 顺序，而是由多个带元数据的优化模块注册、排序、校验依赖后执行。

一句话版本

原来像是 RunTier2Pipeline 里手写一串函数调用； 现在每个优化 pass 被包装成 Tier2OptimizerModule， 模块声明自己属于哪个 phase、需要哪些分析事实 Requires、 产出哪些分析事实 Provides，再由 BuildModulePlan 统一组装执行。

整体执行流

输入函数

FuncProto bytecode

VM 收集热点后，MethodJIT 把字节码函数构造成 Tier2 IR。

Tier2 IR

Function Blocks Instrs

IR 上挂着 AnalysisResult，保存 range、shape、call ABI 等分析结果。

模块计划

BuildModulePlan phase order

各领域文件通过 RegisterModuleBuilder 注册模块，plan 按 order 排出 phase 顺序。

依赖校验

Requires Provides

执行前检查：某个模块要求的事实，是否已经由前面的模块提供。

优化后 IR

native lowering diagnose

每个模块运行后可记录 timing、remarks、IR snapshot，再进入 native emission。

核心类型对应关系

名字 含义
Tier2OptimizerPhase 粗粒度阶段，比如 early canonical、inline、numeric、table lower、loop kernel。
Tier2OptimizerModule 最小优化单元，通常包一条 pass，也可以带 context 和诊断元数据。
Requires 这个 module 运行前需要已经存在的分析事实。
Provides 这个 module 运行后会产出的分析事实。
AnalysisResult 所有 pass 共享的分析结果容器，比如 int range、fixed shape table、call ABI。
Tier2OptimizerContext 单次编译过程共享的上下文，比如 globals、protocol globals、inline 状态、snapshot callback。

为什么叫“模块化”

因为优化 pass 不是只能塞进一个大函数里，而是可以分散在领域文件里注册。 字符串、表、数值、矩阵、循环内核等模块各自维护自己的 builder。

这让新增优化更像“插入一个带 contract 的模块”，而不是“在一条长长的手写调用链里找位置”。

模块内部长什么样

一个 module 本质上是 pass 函数加元数据。

Tier2OptimizerModule{
  Name: "RangeAnalysis",
  Phase: Tier2PhaseNumeric,
  Requires: nil,
  Provides: []string{
    "Int48Safe",
    "IntRanges",
  },
  Run: RangeAnalysisPass,
}

依赖事实怎么流动

例如 OverflowBoxing 需要先有 IntRanges。 所以它必须排在 RangeAnalysis 后面。

RangeAnalysis provides IntRanges OverflowBoxing requires IntRanges

诊断怎么接入

每个 module 执行后，管线可以记录耗时、remarks、IR snapshot。 这就是诊断工具能看到“哪个 pass 改了什么”的基础。

timing remarks snapshot

我说“还有改进空间”的具体原因

当前设计 问题 应该收敛成什么样
BuildModulePlan 按 builder order 追加 phase 如果两个 builder 注册同一 phase，phase 会重复，模块可能被重复执行。 按 phase 分组，phase 列表去重；同 phase 内再稳定排序。
Requires/Provides 是字符串 容易拼错，也无法编译期检查。 改成 typed constants，例如 AnalysisFactIntRanges。
部分 module 写 Provides: nil // Updates existing facts 依赖图不完整，checker 无法知道它真实读写了什么。 明确区分 Reads、Writes、Updates。
每次执行 plan 都做依赖校验 这更像初始化/测试期检查，不应该混进热路径。 构建 plan 时校验一次，或者 debug/test 模式强校验。
Order 字段保留但没生效 读代码的人会误以为 module 内顺序可由该字段控制。 要么实现，要么删掉，避免假接口。

最容易误解的一点

“模块化优化器管线”不等于“自动优化一切”。它只是让优化 pass 的组织方式更清楚： 每个 pass 仍然要自己实现具体优化逻辑。模块化解决的是可维护性、可诊断性、依赖顺序和扩展边界； 性能提升仍然来自具体 pass，例如 table lowering、range analysis、loop kernel、native string lowering 等。

推荐的下一步重构目标

  1. 把 BuildModulePlan 改成 phase 分组模型，避免重复 phase 执行。
  2. 给默认 optimizer plan 加 golden/snapshot 测试，锁住 phase 和 module 顺序。
  3. 把 fact 字符串改成类型化常量。
  4. 补全 module 的读写 contract，让 dependency checker 真正可信。
  5. 把诊断 snapshot 扩展到 pass 失败路径，方便定位坏优化。
