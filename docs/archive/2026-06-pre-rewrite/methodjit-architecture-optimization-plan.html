MethodJIT 架构优化计划

目标是把当前“已经模块化”的 Tier2 优化器继续收敛成可验证、可诊断、可扩展的编译器架构，而不是继续靠人工记忆维护 pass 顺序。

目标状态

MethodJIT 的优化管线应该满足四个条件： pass 顺序可声明、分析事实可校验、诊断输出可解释、Tier1/Tier2 策略边界清楚。 后续新增优化时，开发者应该只需要声明“我属于哪个阶段、读什么事实、写什么事实、失败怎么回退”，而不是手工猜测应该插在哪里。

V8 调研后的设计基准

V8 的现代架构不是一个单体 JIT，而是多层 tiering 加多个明确边界的 compiler pipeline： Ignition 解释器、Sparkplug baseline、Maglev 中层优化器、TurboFan/Turboshaft 高层优化器。 对 gscript 来说，不能照搬复杂度，但应该吸收它的几个结构原则。

V8 设计点 观察 gscript 应该怎么吸收
TieringManager 优化决策和编译 pipeline 分离，decision 里带目标 tier、并发模式和原因。 把 Tier1/Tier2 晋升条件、拒绝原因、blacklist/deopt 原因集中到 tiering policy，不散在 pass 里。
PipelineData 编译过程状态集中在 data 对象里，phase 只通过 data 访问 graph、stats、broker、trace。 让 Tier2OptimizerContext 演进成真正的 pipeline data，承载 IR、analysis、diagnostics、dependencies。
PhaseScope / BeginPhaseKind 每个 phase 都有统一 scope，自动处理统计、临时内存、node origin、trace。 给 MethodJIT module run 包一层标准 phase scope，统一 timing、snapshot、error、fact diff。
Graph verification Maglev 和 TurboFan 在关键阶段后打印/验证 graph，debug 下更严格。 在高风险 lowering、DCE、register allocation 前后加 IR verifier，不靠性能测试发现坏 IR。
CompilationDependencies 优化假设被记录为 dependency，最终安装；假设失效时 deopt/invalidates compiled code。 把 table shape、metatable version、global const、call ABI 等假设从散落 guard 收敛成 dependency registry。
BailoutReason phase 可以显式返回 bailout，pipeline 记录原因并放弃优化。 MethodJIT pass 不应该只返回普通 error；需要区分 compiler bug、unsupported shape、guarded bailout。

优先级清单

优先级 架构问题 当前风险 改造方案 验收标准
P0 phase 重复执行风险 BuildModulePlan 原来直接 append phase；同 phase 多 builder 时会重复跑同一 phase 模块。 已改成 Tier2OptimizerPhaseGroup，plan canonical execution shape 按 group 执行。 已补 TestTier2OptimizerPlanDeduplicatesFallbackPhases。
P0 pass contract 不可信 很多 module 写 Provides: nil // Updates existing facts，依赖图无法表达真实读写。 引入 Reads/Writes/Updates 或完善 Requires/Provides 语义。 所有核心 pass 都声明事实读写；dependency checker 能覆盖主要分析事实。
P0 Tier1/Tier2 可调用策略混淆 MethodJITCallable() 允许部分 vararg 进 Tier1，但 Tier2 仍禁止 vararg；命名容易误用。 拆成 Tier1Callable / Tier2Callable，并补 ABI 说明。 vararg/no-OP_VARARG 测试覆盖 Tier1；Tier2 放开前有独立设计。
P1 依赖校验位置不合理 每次 run plan 都做 dependency validation，和“初始化/测试期检查”的注释冲突。 构建默认 plan 时校验一次，缓存 validated plan；测试开启严格校验。 热路径不再重复校验；测试仍能捕获缺失依赖。
P1 全局 init 注册难测试 module 注册顺序隐式，测试无法简单构造隔离 registry。 提供显式 DefaultModuleRegistry()，init 只做兼容层或逐步移除。 单测可以创建临时 registry，不污染全局状态。
P1 fact 使用字符串 拼写错误运行时才发现；重构不安全。 定义 type AnalysisFact string 和常量集合。 module metadata 不再直接写裸字符串。
P1 诊断只覆盖成功路径 module 出错时缺少失败前后 IR、耗时、依赖状态。 snapshot callback 支持 failure snapshot 和 module error record。 故意失败的 pass 测试能看到失败 module 和失败时 IR。
P2 Order 字段未生效 字段存在但没有参与排序，会误导后续开发者。 要么实现 phase 内 module order，要么删除字段。 代码和注释一致，没有“未来保留但看似生效”的接口。

SOLID 对应关系

原则 架构动作
SRP module 只负责一个 pass；registry 只负责注册；plan builder 只负责排序校验；diagnose 只负责观察。
OCP 新增优化通过 module/phase/fact contract 扩展，而不是修改大函数调用链。
LSP 所有 module 必须遵守相同 contract：声明依赖、返回新 Function、错误可诊断。
ISP 拆分 Run、RunWithContext、diagnostic hook，避免每个 pass 都依赖一个大上下文。
DIP optimizer 依赖 module interface/contract，不依赖具体 pass 文件和 init 顺序。

编译器/JIT 角度

  • phase 是编译器 pipeline 的粗粒度 barrier。
  • fact 是 analysis pass 和 transform pass 之间的 contract。
  • validator 是 pass manager 的安全网。
  • diagnose 是可解释 JIT 的观测层。
  • Tier policy 是运行时调度和 native ABI 的边界，不应混在优化 pass 里。

提交策略

  1. 每个阶段单独提交，不和性能优化混在一起。
  2. 阶段 A/B/C 属于架构重构，提交信息明确“不改变优化语义”。
  3. 如果某个提交改变 JIT 晋升策略，必须单独提交，不能写成纯重构。
  4. 每个提交至少跑 go test ./internal/methodjit ./internal/vm ./internal/runtime -count=1。
  5. 涉及 plan 执行顺序时，补 golden test；涉及性能热路径时，再跑 strict guard。

不要做的事

  • 不要继续扩大隐式全局 registry，而没有测试隔离能力。
  • 不要把裸字符串 fact 继续扩散到新 pass。
  • 不要让诊断逻辑反向污染优化 pass 的核心逻辑。
  • 不要在“重构”提交里悄悄改变 Tier1/Tier2 晋升策略。
  • 不要为了快速插 pass 绕过 dependency checker。
